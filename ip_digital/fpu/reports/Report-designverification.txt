DESIGN UNDER TEST OVERVIEW
---------------------------
Block       : fpu_top — IEEE 754 single-precision FPU
RTL scope   : 10 SystemVerilog modules, 2,583 lines total
Sub-units   : FMA (fused multiply-add), CVT (convert), NONCOMP (non-computational
              ops: FMIN/FMAX/FCLASS/FSGNJ), DIVSQRT (division / square-root)
Pipeline    : EX1 → EX2 → EX3a → EX3b → EX4 (6-cycle FMA latency, full throughput)
Interface   : 32-bit operands (src_a_i, src_b_i, src_c_i), 3-bit rounding mode,
              5-bit fflags_o (IEEE 754 exception flags), valid_i / valid_o handshake

XYZ #4.1 — CRITICAL PATH TIMING CLOSURE (12.75 ns → 12.03 ns)
  Issue: TT corner WNS = −0.390 ns (arrival 12.752 ns, required 12.362 ns at 80 MHz),
  blocking sign-off. SS corner at −92.593 ns appeared catastrophic, masking the
  root cause.

  Root cause analysis (multi-layer):
    Layer 1 — SS false alarm: 34 sky130 lpflow power-isolation cells
    (lpflow_isobufsrc_1, lpflow_inputiso1p_1) mapped by abc at SS corner were
    derated 30+ ns, inflating the reported SS WNS by ~90 ns. These cells implement
    X = A AND NOT(SLEEP) and should never appear in the core datapath.

    Layer 2 — True bottleneck (TT): a single high-fanout nor2_1 cell (_5392_)
    at the EX3 stage of fpu_fma drove the full 29-bit LZD (leading-zero detect)
    priority-encoder tree, producing a 12.75 ns combinational path that violated
    the 12.50 ns cycle budget by 390 ps.

  Fix — lpflow pre-filter (p6_synth.py):
    Accomplished: eliminated 30+ ns SS derating without any RTL change,
    Measured by: SS WNS improving from an unmeasurable −92.593 ns to a steady
    −84.202 ns (the remaining SS gap is real pre-layout pessimism, advisory),
    By doing: implementing _filter_liberty_lpflow() in p6_synth.py to write a
    sanitized liberty copy (sky130_fd_sc_hd__tt_025C_1v80_nolpflow.lib) before
    abc mapping — removing 34 lpflow cells via regex cell-block scan.

  Fix — EX3 pipeline split (fpu_fma.sv):
    Accomplished: closed 80 MHz TT timing with +0.131 ns WNS (521 ps improvement),
    Measured by: TT arrival time falling from 12.752 ns to 12.028 ns, slack
    flipping from −0.390 ns to +0.131 ns, and P3 20/20 tests still passing after
    the structural change,
    By doing: inserting one pipeline register (r2b_*, 13 flops) between the
    adder/subtractor and the LZD encoder in EX3, splitting the 12.75 ns path
    into two ~6 ns half-stages:
       Before: r2 → [compare + add/sub + LZD + zero-detect] → r3  (12.75 ns)
       After:  r2 → [compare + add/sub] → r2b → [LZD + zero-detect] → r3 (~6 ns)
    FMA latency increased 5 → 6 cycles (throughput unchanged; valid_o handshake
    absorbs the extra cycle with no cocotb test changes beyond FMA_LATENCY = 6).

  Collaboration protocol:
    The root-cause diagnosis was shared with the design team as a structured
    3-layer report (SS false alarm → lpflow fix → true EX3 bottleneck → pipeline
    split) before any RTL was touched. This separation of concerns — isolate the
    library bug first, then address the architectural path — prevented wasted
    iteration on timing that appeared worse than it was.

XYZ #4.4 — VPI WRITE RACE DEBUG (pyUVM / Icarus Verilog)
  Issue: 4/4 UVM tests failing on initial integration; observable symptoms
  (wrong scoreboard result, valid_o timeout, spurious mismatch) masked three
  independent root causes operating simultaneously.

  Root cause analysis (three layers):

    Layer 1 — Write order race in combinational mux (test_noncomp):
    fpu_result_mux.sv selects sub-unit outputs based on op_i[5:4] via a purely
    combinational priority mux. Writing valid_i=1 BEFORE op_i caused a zero-
    duration simulation delta where fma_valid_i = (valid_i & sel_fma) was
    asserted with op_i still at 0x00 (FADD unit). The FMA pipeline latched this
    spurious transaction, producing valid_o=1 five cycles later with int_result=0.
    The scoreboard paired this with the first real FCLASS input (expected
    int_result=0x10), recording a false mismatch.
    Fix: write all operands (op_i, src_a_i, src_b_i, src_c_i, rm_i) before
    asserting valid_i=1 — guaranteed by write order in FPUDriver._drive().

    Layer 2 — VPI timing race with Icarus Verilog clock edge (test_divsqrt):
    The cocotb driver coroutine resumes from get_next_item() at an arbitrary
    simulation timestamp. In Icarus Verilog, if a rising clock edge fires at
    the same simulation time as a VPI write, the callback evaluation order is
    non-deterministic. This caused valid_i=1 and the clock edge to be processed
    in reverse order — valid_i was seen as 0 by the DUT at the latching edge,
    so the divsqrt FSM never transitioned out of S_IDLE. valid_o was never
    asserted and the driver timed out after 200 cycles.
    Fix: await RisingEdge(clk) at the top of _drive() synchronizes the driver
    to the post-edge quiet window, guaranteeing all subsequent VPI writes reach
    the DUT before the next rising edge.

    Layer 3 — Stale pipeline capture in output monitor (test_random):
    After reset, the DUT's noncomp unit may have valid_o=1 asserted from a
    prior cocotb test phase still draining the pipeline. Without a guard, the
    FPUOutputMonitor captured this stale result and wrote it to the output FIFO.
    The scoreboard consumed it as the first real output, pairing it with the
    first random transaction input — producing a spurious mismatch on whatever
    operation was randomly selected first.
    Fix: seen_valid_i boolean flag — the output monitor only forwards output
    captures after valid_i has been seen asserted at least once in the current
    UVM test. This discards all pre-driver pipeline state.

  Outcome: all 4/4 UVM tests PASS (test_noncomp: 0 fails / 49 txns,
  test_arith: 0 fails / 10 txns, test_divsqrt: 0 fails / 7 txns,
  test_random: 0 fails / 60 txns). Total scoreboard checks: 126.
