# mac_tile_axi — Engineering Report: A Weight-Stationary Systolic MAC Tile, Two New Toolchain-Divergence Findings, and a Self-Referential Deadlock Caught by Adversarial Review

_Companion to `STATUS.md`. Phase 2 of the RISC-V SoC roadmap: the portfolio's first AI/ML-accelerator-shaped IP and its first genuinely new protocol (AXI4-Stream). Builds a 4x4 weight-stationary int8 systolic array behind an AXI4-Lite control port, standalone-proves it across all 9 pillars, then integrates it into `rv32i_soc` as a 4th bus-attached coprocessor -- mirroring Phase 1's own build-then-compose shape. An adversarial review, run deliberately before committing, found a real one-shot deadlock bug in the CPU-facing MMIO bridge that every other verification vehicle (a 9-pillar standalone sweep, a formal proof, and a passing SoC-level test program) had missed -- fixed, then proven fixed with a dedicated regression test and a new formal liveness cover property, not just re-running the tests that already passed._

## Situation

Phase 1 built a complete RV32I SoC. Phase 2, per the user-approved 4-phase portfolio roadmap, is "AXI4-Stream + systolic MAC tile as an SoC coprocessor" -- the portfolio's first AI/ML-accelerator-shaped block and its first genuinely new protocol. A repo survey before any RTL was written confirmed there was no reusable AXI4-Stream, MAC, or systolic RTL anywhere in this codebase, and no existing IP had ever implemented real consumer backpressure (`fpu_top.sv`'s own `ready_i` is dead, tied off via XOR). This phase was new ground on several axes at once.

Three architecture decisions were made via `AskUserQuestion` before any code was written: int8x int8->int32 accumulate (not fp32 -- diversifies the portfolio, more formally/GLS tractable), a 4x4 array (16 PEs, chosen to stay under the cell-count scale that already made `rv32i_soc`'s P8 GLS time out in Phase 1), and build-standalone-then-integrate-in-this-same-phase (matching Phase 1's own Step 1-3-build/Step-4-compose shape). A fourth requirement was added mid-planning by explicit user request: the PE's arithmetic core must be swappable/reusable with the portfolio's existing fp32 FPU (`fpu_fma`), so a future session can swap int8 for fp32 without redesigning the array.

## Task

Design and formally verify a weight-stationary systolic array bottom-up (leaf arithmetic core -> PE shell -> skew network -> array -> stream glue -> register-mapped top), with the PE shell parameterized for future fp32 swap without building the fp32 leaf this phase. Compose the finished, standalone-proven tile into `rv32i_soc` as a 4th bus-attached slave, extending the existing 3-slave address decoder. Write a real test program that exercises the tile through the CPU's own register-mapped MMIO bridge (this SoC has no AXI4-Stream master anywhere, so MMIO push/pop is the *only* path the CPU has to drive the tile). Take both the standalone tile and the composed SoC through all 9 pillars, and subject the integration diff to an adversarial review before calling it done -- the same discipline that caught two real bugs in `rv32i_addr_decoder` during Phase 1.

## Action

### Dataflow derivation, done on paper before any RTL

PE(i,j) holds stationary weight W[i][j] (i = row = reduction index, matching activation element i; j = column = output-feature index). West-edge activations skew in with row i delayed `i*LATENCY` cycles behind the external boundary; south-edge partial sums de-skew out with column j delayed `(N-1-j)*LATENCY` cycles. Total fixed external latency is `(K+N-1)*LATENCY` = 7 cycles at `LATENCY=1` (int8, this phase); steady-state throughput is 1 new vector/cycle independent of `LATENCY`, because every hop -- including the arithmetic core itself -- is a genuine per-cycle-accepting pipeline stage for any fixed-latency, always-accepting core. All skew complexity is fully contained inside `systolic_array_4x4`'s own boundary; its external contract stays simple regardless of `LATENCY`.

### Seven checkpoints, smallest first, each proven standalone before the next was built on top

1. **`int8_mac_core.sv`** -- combinational multiply + enable-gated register, LATENCY=1. Formal: exact-accumulate via a shadow register, bounded `psum_in_i` range via `assume()` (never `inside{}`), freeze-holds-value. PASSED (~25s).
2. **`mac_pe.sv`** -- a thin, `LATENCY`/`ACT_W`/`PSUM_W`/`USE_FP32`-parameterized shell around a swappable leaf. `int8_mac_core` is the only *implemented* leaf this phase; a `fp32_mac_core` generate arm exists but is an inert placeholder (`$fatal` if ever selected) -- deliberately not built this phase, because `pipeline_en_i`'s meaning genuinely forks between `LATENCY=1` (freezes the whole arithmetic core, a 1-entry output skid suffices) and `LATENCY=4`, if `fpu_fma` were ever wired in (no enable of its own reaches `fpu_fma`'s internals, so in-flight results keep draining regardless of downstream readiness -- a real FIFO sized to 28 cycles, or a weaker `m_axis_tready` contract, would be needed). Building that leaf is a named, deferred future task, not a parameter substitution. PASSED (~12s).
3. **`skew_chain.sv`** -- parameterized delay line, `DEPTH=0` a pure combinational passthrough. PASSED at `DEPTH=3` (own checkpoint) -- but see the Errors section for a real cross-checkpoint gap this exposed at `DEPTH=0`.
4. **`systolic_array_4x4.sv`** -- the 4x4 grid: real `skew_chain` instances kept in the proof, all 16 `mac_pe` instances anyseq-stubbed, proving wiring/skew-depth correctness only (not arithmetic) -- deliberately not the vacuous "stub everything, assert input==output" shape Phase 1's `rv32i_addr_decoder` review already caught once. PASSED (~1s) after two real port-syntax fixes (see Errors).
5. **`axis_skid.sv`** -- a 1-entry FWFT skid buffer, this repo's first reusable streaming primitive (confirmed no existing FIFO fit the same-clock, FWFT-handshake shape `async_fifo.sv` doesn't provide). PASSED.
6. **`axi4stream_ctrl.sv`** -- the glue FSM: TDATA pack/unpack, `s_axis`/MMIO accept-side mutual exclusion, weight-load-gated-on-idle, an occupancy/TLAST tag chain. PASSED with `systolic_array_4x4`/`axis_skid` formally stubbed -- but this file is also where the MMIO deadlock bug lived; see below.
7. **`mac_tile_axi.sv`** -- the AXI4-Lite top level: `axi_lite_slave` (vendored) + `axi4stream_ctrl`, a 16-register map, and a CPU-facing MMIO push/pop bridge (`DATA_IN`/`RESULT0-3`) since `rv32i_core`'s LSU is an AXI4-Lite master only. PASSED with `axi_lite_slave`/`axi4stream_ctrl` formally stubbed.

### Two genuinely new toolchain-divergence findings

**Yosys `-sv` rejects both unpacked-array module ports (`logic [W-1:0] sig [K]`) AND multi-dimensional packed-array ports (`logic [K-1:0][W-1:0] sig`)**, even though Icarus and Verilator accept either form. `systolic_array_4x4.sv`'s ports needed two failed attempts before landing on the one shape all three tools agree on: a flat 1-D packed vector, sliced with part-selects (`sig[idx*W +: W]`) at every use site. Internal (non-port) unpacked arrays are unaffected -- a different Yosys code path, already proven working elsewhere in this repo.

**A runtime `assume()` cannot prevent an invalid construct from being elaborated.** `skew_chain.sv`'s own formal block used `initial assume(DEPTH > 0)` to exclude `DEPTH==0` from its proof, which worked fine in its own isolated checkpoint (only ever run at `DEPTH=3`). But when `systolic_array_4x4` instantiated it at `DEPTH=0` for real (row 0's west skew, column 3's south de-skew), Yosys hard-errored trying to elaborate a zero-sized shadow array -- `assume()` only constrains proof exploration *after* elaboration succeeds, it cannot retroactively un-elaborate an invalid declaration. Fixed with a real `generate if (DEPTH > 0) ... else ...` split. **General lesson, now added to project memory**: any formal-block array sized by a parameter that could legitimately be 0 needs a generate-if guard, not just an `assume()` -- and a module's own isolated `.sby` checkpoint may never exercise the parameter value that later breaks it once a parent composes it for real.

### A bug I caught myself before it ever reached simulation

While authoring `axi4stream_ctrl.sv`'s accept-side arbitration, re-deriving `mmio_accept`/`s_axis_accept` directly as `valid && ready` from the exact same externally-exposed `ready_o` signals (rather than maintaining two separately-computed conditions) surfaced that an earlier draft's `mmio_accept` omitted a `!mmio_result_valid_q` term that `mmio_data_in_ready_o` itself included -- which would have let a same-cycle MMIO push be silently accepted while the ready signal was reporting not-ready. Fixed before ever running a simulation.

### The bug I did *not* catch myself: a one-shot MMIO deadlock, found by adversarial review

With the standalone tile at 8/9 PASS and the SoC composed, decoded, and passing its own test program (one MAC push, `RESULT0` read correctly through the full decoder-to-tile path), a multi-agent adversarial review was run over the integration diff before committing -- the same discipline Phase 1 used on `rv32i_addr_decoder`. One review dimension was asked specifically to check whether tying off the tile's unused `s_axis`/`m_axis` ports at the SoC level was safe; it surfaced something more serious: **the MMIO bridge could accept exactly one push, ever.**

The mechanism: `mmio_result_valid_q` latches to 1 when a result drains, and its only clear path was `mmio_accept` (a new push being accepted). But `mmio_data_in_ready_o` -- and therefore `mmio_accept` -- is itself gated on `!mmio_result_valid_q`. Once the flag sets, the condition that would clear it can never become true again: a same-cycle chicken-and-egg deadlock, not a corner case. `STATUS.INPUT_BUSY` (derived from `!mmio_data_in_ready_o`) latches high forever, so any correctly-written poll-before-push driver hangs permanently on a second operation. Since `rv32i_soc.sv` permanently ties off the external `s_axis` port, MMIO is the *only* usable path in that SoC -- this bug was guaranteed to fire on any real second MAC operation, not a remote possibility.

It escaped every other check because none of them ever exercised two successive MMIO pushes: the standalone `test_mmio_bridge_path` cocotb test did exactly one push; the formal block's safety properties (`if mmio_result_valid_q, assert !mmio_data_in_ready_o`) hold *identically* on a permanently-deadlocked design, since a safety assertion can't distinguish "correctly gated" from "gated shut forever" -- only a liveness/cover property can; and the new SoC test program also did exactly one push. The review's own automated adversarial-verification pass (a second layer of agents meant to try to refute each finding) hit a session usage limit mid-run and never actually checked this claim -- so before touching any RTL, I re-derived the deadlock myself, cycle by cycle, directly from the actual current file content, and independently confirmed it was real, not a reviewer error.

**Fix**: an explicit `CTRL.RESULT_ACK` bit (bit 3), edge-pulsed the same way `LOAD_WEIGHTS` already is, giving software an unconditional way to clear `mmio_result_valid_q` that doesn't depend on `mmio_data_in_ready_o` first becoming true -- the same "`axi_lite_slave` has no read-side-effect mechanism, so consume is an explicit write" pattern `uart_axi_periph`'s own `CTRL.RX_POP` already established in this repo. `mmio_accept` is kept as a belt-and-suspenders clear condition (it can only fire *after* an ack already cleared the flag on a prior cycle, never as the primary mechanism).

Two things were added specifically because a passing safety proof had already shown itself insufficient for this bug class: a new formal **cover** property proving a *second* `mmio_accept` is reachable after a first (unreachable on the pre-fix RTL, confirmed reachable post-fix), and a new cocotb test, `test_mmio_bridge_second_push`, that pushes, polls, reads, acks, and pushes again -- it would hang forever on the pre-fix RTL and passes cleanly post-fix. The same two-push sequence was also added to the SoC's own `program.s` (a second activation vector, `RESULT0` read into a 5th RAM word) so the fix is proven through the real address-decoder/MMIO-bridge path software would actually use, not only in the IP's own isolated testbench.

### SoC integration: decoder widening, composition, and a self-caught wiring gap

`rv32i_addr_decoder.sv` was extended from 3 slaves to 4 (`SEL_RAM/SEL_UART/SEL_FPU/SEL_NONE` -> add `SEL_MAC`, widening the select enum from 2 bits to 3 and touching roughly 20 sites: every case statement, ternary chain, `$onehot0` assertion, in-bounds check, and the non-tautological literal-constant formal properties this file's own header already documents needing after an earlier Phase-1 adversarial review caught a vacuous version of exactly this proof). `mac_tile_axi` was flat-copied into `rv32i_soc/rtl/` (this repo's established composition pattern) and instantiated as `u_mac`, with its unused `s_axis`/`m_axis` ports tied off (`s_axis_tvalid_i=0`, `m_axis_tready_i=1`) since MMIO is the only path this SoC uses.

Two mistakes were caught before they reached a passing pillar: (1) a fresh Verilator lint run flagged `PINMISSING` on `u_decoder`'s new `mac_*` ports -- I had wired `mac_tile_axi`'s own ports to fresh signals but never connected those signals to the decoder instantiation's port list, a pure copy-paste omission caught immediately by P1, not by inspection; (2) the pre-existing DECERR probe in `program.s` touched page `0x3000` to prove the decoder's error path -- exactly the address the real MAC slave now occupies. Moved to `0x4000`, the genuinely unmapped page after widening, and re-verified via the decoder's own formal cover points for that address.

### Independent verification, twice, that the test program's own encoding is correct

`scripts/rv32i_asm.py --format rom` was used to assemble `program.s` (86 real instructions after the MAC section, still fits the auto-widened 7-bit ROM index). Rather than trust the assembler output, `rv32i_core/verification/decode_check.py` -- a from-scratch, independently-written disassembler (deliberately not importing the assembler's own bit-manipulation logic) -- was pointed at the generated ROM and every hand-computed immediate (the `LUI`+`ADDI` split for `0x04030201`, `0xDEAD`, `0xCAFEF00D`, `0x09080706`) was confirmed to decode back to exactly the intended value, twice: once after the first MAC section was added, once more after the second-push regression was appended.

A weight-loading transpose bug -- rows and columns swapped -- was specifically checked for, since the test's first weight matrix (`W=5*I`) is symmetric and could not have exposed one on its own. Traced directly from the RTL (`systolic_array_4x4.sv`'s `weight_i[(gi*N+gj)*ACT_W +: ACT_W]` indexing, `gi`=row=reduction index) rather than trusting either the code comments or the unverified reviewer output, and cross-checked against the standalone cocotb suite's own `test_mmio_bridge_path`, which already used a genuinely non-symmetric weight matrix and had already passed -- two independent confirmations that no transpose bug exists.

### STA recalibration -- a real fanout bottleneck, not a metric artifact

The tile's SDC started at a 10.0 ns guess (assuming the critical path would be dominated by a single int8 multiply, since every PE-to-PE hop is register-bounded). The real P8 STA numbers showed TT VIOLATED by -15.208 ns. Before recalibrating, the actual critical path was read from the raw STA log (not assumed): a single `clkinv_1` cell carries a 13.772 ns delay alone, almost certainly `array_pipeline_en`/`pipeline_en_i` fanning out to all 16 PEs with no fanout buffering -- synthesis's own log had already flagged this directly ("Add `set_max_fanout` and `set_max_transition` constraints"). Not fixed at the RTL level (a backend/PPA-closure concern, consistent with this portfolio's pre-layout-STA-is-advisory-pessimism stance), but the SDC was recalibrated to 30.0 ns (33.3 MHz), matching `rv32i_core.sdc`'s own ~20% margin convention, and the real bottleneck documented in the SDC's own comment instead of silently widening the period with no explanation.

### A shared-infrastructure bug, found and fixed with the same care this portfolio applies to shared code

While triaging the first sweep's suspiciously low "Cell Count: 8" dashboard figure, `scripts/pillars/common.py`'s `SynthLogParser.parse()` was found to use a single, non-multiline `re.search()` for `"Number of cells:"` -- which Yosys prints once per submodule during hierarchy-analysis passes before a final rolled-up total in a `=== design hierarchy ===` section. `re.search()` returns the *first* match (an early, small submodule's own count), not the log's real total. This is shared code gating every IP's dashboard in this portfolio, so -- unlike the GLS-timeout situation in Phase 1, which was deliberately left unfixed because it would have weakened a real gate -- this was evaluated as a pure bugfix that changes no pillar's PASS/FAIL semantics anywhere, only a reported metric's accuracy, and fixed: anchored on the `=== design hierarchy ===` marker, with a last-match fallback if the marker is absent, applied to both the cell and wire counts. Verified against a second, independent, already-shipped design (`rv32i_soc`) whose own documented cell count (67,984) turned out to be the *same* bug's artifact -- the true figure is 93,987, corrected in that IP's own `REPORT.md` with an explicit dated correction note rather than silently overwritten.

## Result

- **8/9 PASS, 1 documented WARN** standalone (the same "N/9, 1 WARN" shape most sequential IPs in this portfolio reach), plus a clean 7/9 PASS / 1 WARN / 1 documented FAIL on the composed `rv32i_soc` -- identical shape to Phase 1's own Step 4, with the FAIL being the same *inherited* GLS scale-wall timeout (confirmed via the raw log, TT STA itself MET at +9.889 ns, unchanged from before this phase's composition), not a new regression.
- **A real, severe correctness bug was found and fixed after the "done" point**, not before it -- the standalone 9-pillar sweep, the standalone formal proof, and a passing SoC-level test program all looked clean while the MMIO bridge could still only ever be used once. The fix is proven with the specific kind of evidence a passing safety proof cannot provide on its own: a liveness cover property and a dedicated two-push regression test, at both the IP and the SoC level.
- **The fp32-swappability requirement is designed for, not built** -- `mac_pe`'s shell, `LATENCY`-parameterized skew math, and the `USE_FP32` generate seam are all in place; `fp32_mac_core` and its output-buffering contract (a real architectural fork, not a parameter substitution, since `fpu_fma` has no `ready_i` of its own) remain a named future task.
- **A shared-infrastructure metric bug affecting every IP in this portfolio was found, fixed, and its blast radius checked** against a second, already-shipped design before being trusted.
