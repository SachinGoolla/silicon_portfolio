# mac_cluster — Engineering Report: A 2x2 Mesh NoC, Three Races Found by Formal and a Fourth Found by a Second Testbench, and a Genuinely Clean GLS Result

_Companion to Phase 3 of the RISC-V SoC roadmap: "scale the MAC tile to multiple tiles connected by a small NoC" — the portfolio's first genuine network-on-chip design (routers, a flit format, multi-hop XY routing, deadlock-freedom reasoning). Builds a parameterized 5-port mesh router once, composes it into a 2x2 mesh, wraps each of 4 `mac_tile_axi` instances with a network interface, and integrates the whole cluster into `rv32i_soc` as a 5th bus-attached slave. Formal verification caught three genuine structural races during the router/NI build — the same "live-recomputed multi-source state feeding a multi-cycle consumer" bug class recurring at three different levels of composition. A fourth race, in the cluster's own CSR mirror, escaped formal by construction (it spans a hardware pipeline-latency interaction with a software polling protocol, outside any single module's proof cone) and was only caught because a second, independently-written testbench (Verilog tasks, not cocotb/Python) happened to hit a timing window the first one had been silently lucky to avoid._

## Situation

Phase 2 built one 4x4 systolic MAC tile. Phase 3, per the user-approved roadmap, scales this to multiple tiles connected by a small NoC — genuinely new ground: no router, crossbar, or flit-format RTL existed anywhere in this repo before this phase. Two reusable primitives existed to build on: `rr_arbiter` (a proven round-robin arbiter, but with liveness proven only under `assume(!burst_lock_i)` — real burst-hold liveness unproven) and `axis_skid` (Phase 2's own 1-entry FWFT buffer).

Two architecture decisions were confirmed via `AskUserQuestion` before any code was written: the mesh carries tile-to-tile dataflow traffic, not CPU control (the CPU still reaches each tile via an extended AXI4-Lite decoder); and a 2x2 mesh with XY (dimension-order) routing, deadlock-free by construction with no virtual channels needed.

## Task

Build a parameterized 5-port router bottom-up (routing-decision leaf → router → 2x2 mesh → per-tile network interface → cluster top), proving each checkpoint standalone before composing the next, matching this roadmap's own established discipline. Compose the finished cluster into `rv32i_soc` as a 5th bus-attached slave, extending the existing 4-slave address decoder. Write an independent second testbench (Verilog, not cocotb) for the standalone cluster's own P4 Verilator sim — not just a formality, but a genuine cross-check with a different AXI read cadence than the Python/cocotb harness. Take the standalone cluster and the composed SoC through all 9 pillars.

## Action

### Six checkpoints, smallest first

1. **`xy_route.sv`** — pure combinational routing decision, exhaustive 16-case literal truth table. PASSED.
2. **`requant.sv`** — saturating fixed-shift int32→int8, `$signed()` cast applied deliberately (an unsigned shift produces correct-looking answers only for positive inputs — the P3/P4 demo's own weight/activation values were chosen specifically to exercise both saturation directions and a negative in-range value, not just possible-in-principle). PASSED, cover reachable both directions.
3. **`mesh_router.sv`** — the 5-port router: per-port `axis_skid` + `xy_route`, per-output `rr_arbiter#(.N_REQ(4))` (exact, not approximate — under XY routing and no-U-turn, every output has exactly 4 possible requesters, landing precisely on `rr_arbiter`'s proven `{4,8,16}` sweep set). This checkpoint is where the two most serious bugs of this phase were found — see below.
4. **`mesh_2x2.sv`** — 4 real routers composed via a ring-topology neighbor wiring, boundary ports tied off with a checked (not assumed) silence property. PASSED, including reachability covers for both directions of the genuine 2-hop XY turn.
5. **`tile_ni.sv`** — the network interface: mesh-ingress→requant→tile injection, tile egress→mesh-forward-or-CPU-capture, CPU entry/exit CSR glue. A third race was found and fixed here (see below).
6. **`mac_cluster.sv`** — top-level composition: inline 5-way AXI4-Lite decoder (4 tile pages + 1 shared NI-CSR page), 4x `mac_tile_axi` + 4x `tile_ni` + `mesh_2x2`, lint-clean after fixing a real decoder bug (see below).

### Bug 1 — a wrong architectural assumption, caught by formal, not assumed away

The approved plan believed single-flit packets meant `burst_lock_i` could stay tied to 0, structurally discharging `rr_arbiter`'s own `assume(!burst_lock_i)` liveness-proof gap for free. This was **wrong** — it conflates "packets are 1 flit long" with "grants never need holding across cycles." Without holding, `rr_arbiter`'s rotating pointer can swap the winning input mid-flight before the downstream actually consumes it, silently changing the presented flit while VALID stays asserted — a real AXI-stream VALID-STICKY violation, caught as an actual BMC counterexample at depth 5. **Fixed** by tying `burst_lock_i=1'b1` permanently, with `last_i` wired to each output's own transfer condition. This means the design's liveness under real backpressure now *inherits* `rr_arbiter`'s own already-documented burst-hold liveness gap, rather than the newly-discharged-for-free gap the original plan claimed — the file's own header comment was rewritten to state this honestly rather than leave the incorrect original claim standing.

### Bug 2 — a deeper race found only after deliberately increasing proof depth

Even after the `burst_lock_i` fix, a BMC counterexample surfaced at depth 8 (not depth 5 — found by deliberately re-running at greater depth as a sanity check after the pattern of the first bug): a port being drained *this* cycle could simultaneously feed a stale request into a *different* output's next-cycle grant decision — but by the time that grant becomes visible one cycle later, the port's buffer has already been refilled with unrelated content. Diagnosed by compiling SymbiYosys's own auto-generated witness testbench directly with Icarus and injecting `$display` statements reading internal signals — precise cycle-by-cycle confirmation of the exact mechanism, not a guess. **Fixed** by masking every request term with `&& !m_ready[port]` (20 total terms across all 5 output request equations). Re-verified PASSED at depth 10, then depth 15 as an extra sanity check.

### Bug 3 — the same race class, recurring at a different composition level

`tile_ni.sv`'s ingress mux originally re-evaluated `mesh_in_valid_i ? requant_out : entry_data_q` combinationally every cycle. If a CPU-injected entry was being presented (unconsumed) and mesh traffic then became live, the presented data could silently swap sources mid-transaction — the same bug shape as Bug 1/2, one level up. Found as a real BMC counterexample against the file's own VALID-sticky property. **Fixed** with a latched `src_is_mesh_q` decision, updated only when idle or just-consumed — mirroring `axis_skid`'s own FWFT discipline. **General lesson, now proven three times in this phase**: any two-source arbitration feeding one valid/ready-protocol consumer needs a *latched* "who's presenting" decision, never a live, combinationally-re-evaluated one.

### Bug 4 — the race formal structurally could not have caught, found by a second testbench

With all 6 checkpoints formally proven and the standalone P3 cocotb test passing cleanly against an independent Python golden model, an independently-written Verilog testbench (`tb_mac_cluster.sv`, plain `always`/tasks, not cocotb) was built for P4 — not a formality, but this repo's own established discipline of building a second harness with a genuinely different timing cadence. It failed on its first run: the second of two exit-result reads returned a *torn* mix — `RESULT0` still showing the *first*, already-consumed result while `RESULT1-3` correctly showed the second.

Root cause, traced via cycle-accurate `$display` tracing of `mac_cluster.sv`'s own CSR mirror logic: `NI_STATUS.EXIT_VALID` and `NI_EXIT_RESULT0-3` are both driven through the same 2-cycle `hw_we_i → hw_we_q → reg_q` pipeline inside `axi_lite_slave`, and update *simultaneously* on the cycle a genuinely new result is captured. The problem is earlier: `tile_ni`'s own `exit_valid_q` can legitimately go 1(old, unacked)→0(exactly one cycle, if a new result is already waiting)→1(new) — faster than a multi-cycle AXI read can reliably observe the intermediate 0. A poller that issues an ack and immediately re-polls STATUS can observe a stale "still 1" echo of the transaction it *just* consumed, mistake it for fresh, and begin reading RESULT0-3 exactly in the 2-cycle window before the genuinely-new snapshot has finished propagating into `reg_q` — landing the multi-word read sequence squarely across the update boundary.

This is fundamentally a hardware/software protocol gap, not a hazard any single module's own formal proof cone could see: it spans `axi_lite_slave`'s write-pipeline latency, `mac_cluster`'s CSR mirror, and a *multi-cycle software polling sequence* — three levels plus the driver discipline, none of which any one module's `.sby` file has visibility into. **Fixed** with a `exit_seq_q` 1-bit toggle in `tile_ni.sv`, flipped atomically in the same always_ff block that captures a new result (so it can never be observed mid-transition relative to the data it tags), exposed as `NI_STATUS` bit 3. The software contract: track the seq value last consumed per tile, and only trust an `EXIT_VALID=1` reading whose seq differs from that — eliminating the ambiguity entirely, since (proven by direct inspection of `axi_lite_slave.sv`'s write logic) `EXIT_SEQ` and `RESULT0-3` update on the exact same clock edge.

**Confirming the fix is load-bearing, not cosmetic**: both testbenches were instrumented to count and log rejected stale readings before accepting a fresh one. Both — the Verilog TB *and* the cocotb suite — now report rejecting exactly 1 stale reading before accepting the genuine second result. This is the most important confirmation in this finding: **the cocotb test had been passing the whole time for the same reason the Verilator run's first attempt failed differently — pure timing luck.** Its own polling loop carried the identical missing discriminator; it simply never happened to land inside the race window under Icarus's own bus-transaction cadence. A single testbench's clean pass was not evidence of correctness here; a second, differently-timed one was necessary to expose a real, latent bug.

### A related, unaudited finding for a future session

`mac_tile_axi.sv`'s own `RESULT0-3` + `CTRL.RESULT_ACK` (Phase 2) has the *same structural shape* — a continuously-mirrored multi-word register set gated by a level-sensitive valid/ack flag, with the same theoretical exposure to a stale-echo torn read if a second result becomes ready quickly enough after an ack. This has **not** been re-verified this phase — noted as a dated follow-up finding, not a confirmed bug, since `mac_tile_axi`'s own existing test suite has never exercised a "second result already queued and ready to fire the instant of ack" pattern tightly enough to either trigger or rule it out.

### A real lint bug, and a genuinely new toolchain quirk

`mac_cluster.sv`'s own address decoder initially copied `rv32i_addr_decoder.sv`'s in-bounds-check pattern verbatim, producing an ascending (backwards) bit-range select — caught immediately by Verilator's `SELRANGE` warning. Root cause: this decoder's own page size (256B) exactly matches every sub-slave's real width, so there is no "in-page but past-the-slave's-real-width" aliasing slack to guard against in the first place — the check was removed, not patched, once this was understood, and documented as a condition that's vacuously always-true by construction rather than a design gap.

Separately: a `mesh_2x2.sv` lint-waiver comment beginning `// Verilator flags r_in_flit/r_in_valid with UNOPTFLAT...` hard-errored with `Unknown verilator comment` — **Verilator's preprocessor treats any comment (line or block) whose first word is "Verilator"/"verilator" (case-insensitive) as a pragma trigger**, regardless of context, and hard-errors if the rest isn't a recognized pragma keyword. Not previously documented in this project's own memory; fixed by rewording to avoid the trigger word as the first word, and checked (via grep) that no other file in this phase carried the same latent issue. The `UNOPTFLAT` finding itself was investigated genuinely (a real zero-delay path exists through `axis_skid`'s FWFT pass-through when a port's skid is empty and it's the currently-held grant winner) and concluded to be a static-analysis limitation, not a real bug — the `!m_ready[port]` fix from Bug 2 already structurally prevents the hazardous state from being reachable; documented with the full derivation rather than blindly waived.

### SoC integration: a 5th slave, and the DECERR probe moving for the second time

`rv32i_addr_decoder.sv` was extended from 4 slaves to 5 (`SEL_CLUSTER` added — the select enum was already 3 bits wide from Phase 2's own MAC addition, so unlike that phase, no width change was needed this time). `mac_cluster` was flat-copied into `rv32i_soc/rtl/` and wired straight through the decoder with no tie-offs needed (unlike `mac_tile_axi`, `mac_cluster` exposes a single AXI4-Lite port with no external stream/MMIO ambiguity). `program.s`'s DECERR probe — already moved once in Phase 2 (page 0x3 → 0x4 when MAC was added) — collided with the new CLUSTER page exactly as this phase's own plan flagged in advance (§6 risk 6) and moved again, to page 0x5.

The new CLUSTER section of `program.s` loads tile0's `W=5*I` and pushes one activation through the NI's CPU-entry path with `mesh_egress_en` left at its reset default (CPU-exit capture mode) — the result comes straight back out the same tile's own `m_axis` with no mesh hop needed, proving the SoC-level decoder routing and NI CSR wiring without re-proving mesh routing (already proven standalone). The `exit_seq` discriminator is deliberately *not* checked in this assembly section — tile0's first-ever exit capture since reset makes its post-capture seq value unambiguously non-zero, with no prior consumed result to produce a stale echo; a program pushing a second result through the same tile would need the same reject-stale-seq discipline both testbenches implement, and the assembly comment says so explicitly.

### Adversarial review of the cluster sub-decode — no live bug, but a real proof-coverage gap found and closed

Per this phase's own plan (§6 risk 5: "decode logic in this repo is two-for-two on shipping a real bug the first time it's written — budget an adversarial-review pass specifically on the new cluster sub-decode before calling checkpoint 6 done, not just a passing formal sweep"), a dedicated review pass was run over `mac_cluster.sv`'s own internal decode, the `rv32i_addr_decoder.sv` extension, and the `exit_seq_q` fix, before calling this phase done. No live functional bug was found, but three real gaps were:

1. **`mac_cluster.sv`'s formal block proved the write-path literal page-mapping (`awaddr_page → wsel_decode`) but had zero coverage of the read-path (`araddr_page → rsel_decode`)** — a hand-copy of the write-side case statement that could have silently diverged with no formal signal, since `$onehot0` alone can't distinguish "correctly routed" from "consistently but wrongly routed." **Fixed**: added the mirrored read-side literal properties; re-verified PASSED.
2. **`rv32i_addr_decoder.sv`'s own comment claimed pairwise mutual-exclusion coverage for "B/R" but only the B-side (`*_bready_o`) asserts existed** — the R-side (`*_rready_o`) had no equivalent property set. **Fixed**: added the missing 10 R-side pairwise asserts, matching the existing B-side set exactly; re-verified PASSED.
3. **`mac_cluster.sv`'s own header comment overclaimed** that its page size exactly matches every sub-slave's real width, eliminating in-bounds slack — true for the 4 tile pages, but not for the shared CSR page (`NUM_REGS=32` gives it a real 128B footprint inside a 256B page). No aliasing actually results (`axi_lite_slave.sv`'s own `wr_idx/rd_idx < NUM_REGS` gate already returns SLVERR for the 128B of slack, independently of this file's own decode), but the comment was corrected to state the real reason rather than a claim that doesn't hold for one of the five sub-slaves.

Both re-verified formal proofs (mac_cluster's own 6-checkpoint sweep, and `rv32i_addr_decoder`'s SoC-level proof) passed clean after these additions — the gaps were real absences of coverage, not properties that would have failed if written.

### STA — the composition added no new critical path

The standalone cluster's own TT critical path (24.218 ns) traces to `g_tile[0].u_tile/u_ctrl/u_out_skid`'s ready signal fanning unbuffered into the PE array's enable chain — the *same* inherited bottleneck `mac_tile_axi.sdc` already documents, not a new mesh_router-driven path; none of the router/arbiter logic showed up on the worst path in this run. `mac_cluster.sdc` was set to 30.0 ns, matching `mac_tile_axi.sdc`'s own period exactly for that reason. At the SoC level, composing `mac_cluster` in left `rv32i_soc`'s own TT critical path completely unchanged (still `rv32i_core`'s own hazard-forwarding chain, 39.970 ns, unaffected by anything this phase added) — no SDC recalibration was needed at the SoC level at all.

## Result

- **9/9 PASS standalone** — no documented WARN or FAIL anywhere, including a genuinely clean GLS PASS at 118,248 cells, contrary to this phase's own plan, which pre-scoped GLS as *expected to time out* at this scale (§9 risk 1, written before any RTL existed). Worth reporting honestly in both directions: a risk that was flagged upfront and then simply didn't materialize.
- **Four real, structural races found and fixed**, three by formal verification during the router/NI build (the same bug class — live-recomputed multi-source state feeding a multi-cycle consumer — recurring at three different composition levels) and a fourth that formal structurally could not reach (a hardware-pipeline-latency/software-polling-protocol interaction spanning three RTL levels plus the driver), found only because a second, independently-timed testbench was built as a matter of established discipline, not as a formality.
- **The second-testbench discipline is validated concretely, not just in principle**: the cocotb suite that had been "passing" the whole time carried the identical missing discriminator as the Verilog TB that failed on its first run — it had simply never landed inside the race window. Both testbenches now log and confirm an actual stale-reading rejection before accepting the genuine result, proving the fix is load-bearing rather than cosmetic.
- **SoC composition works end to end** at 202,994 cells (7/9 PASS, 1 documented WARN, 1 documented GLS-timeout FAIL — the identical shape Phase 2's own SoC composition already established, confirmed via the raw log as the same wall-clock TIMEOUT root cause, not a new functional regression), with the composition adding no new critical path at either the standalone or SoC level.

## Skills Demonstrated

- Recognizing that "packets are 1 flit long" and "grants never need holding across cycles" are different claims, and that only formal verification — not architectural reasoning on paper — could have caught the gap between them.
- Diagnosing a genuine BMC counterexample by compiling SymbiYosys's own witness testbench directly with Icarus and reading internal signal traces, rather than guessing from the assertion failure alone.
- Recognizing the same race-class signature (live-recomputed multi-source state feeding a multi-cycle consumer) recurring at three different levels of composition, and applying the same class of fix (a latched decision) each time rather than inventing a bespoke workaround per instance.
- Diagnosing a hardware/software protocol race that spans three RTL modules plus a software polling sequence — outside any single formal proof's cone — through cycle-accurate `$display` tracing of a live simulation, and fixing it with a discriminator (a toggle bit) rather than a timing-dependent workaround (a fixed settle delay), after first ruling out the settle-delay approach as fundamentally insufficient (the race window can land between *any* pair of a multi-word read, not at a fixed offset).
- Treating a currently-passing test as inconclusive rather than reassuring when a structurally identical, differently-timed test exposes a real bug — and instrumenting both harnesses to prove the fix is load-bearing (a confirmed rejection occurs) rather than assuming a clean pass means the fix worked.

## Phase 4 Addendum: pyUVM Constrained-Random Coverage Closure

_Everything above this line is the Phase 3 record as it stood at the time, left unmodified. Phase 4, per the user-approved 4-phase roadmap ("UVM constrained-random coverage closure on the richest new block"), targets this IP directly — `mac_cluster` was chosen over `mac_tile_axi` by verification density (118,248 cells vs 16,341, but only 1/1 functional tests vs 9/9, and the largest state space in the portfolio: 20 `rr_arbiter` instances vs 0) and by its own documented history above: three of this IP's four real races were caught by formal, but the fourth (Bug 4) was found only by a second, differently-timed testbench — direct evidence that this IP's own directed-test coverage has a real, demonstrated blind spot in timing/interleaving space that only systematic randomization reliably samples._

### Tooling and architecture

A hand-rolled constrained-random + coverage layer (`random.randint()`/`random.choice()` per-field generators, a ~20-line dict-of-bins `CoverPoint` class), mirroring `fpu_top/verification/uvm/`'s own already-working, zero-dependency pattern in this repo rather than adding `cocotb-coverage` as a new dependency — this repo already had an in-repo precedent for exactly this problem. New tree under `ip_digital/mac_cluster/verification/uvm/`: `mac_cluster_seq_item.py`, `mac_cluster_driver.py` (reuses `test_mac_cluster.py`'s own proven AXI bit-banging verbatim), `mac_cluster_monitor.py` (`MacClusterHierMonitor` — a genuinely independent channel reading `tile_ni`'s internal state hierarchically through `dut.g_tile[t].u_ni.*`, confirmed reachable under Icarus VPI before any checkpoint depended on it), `mac_cluster_env.py`, `mac_cluster_ref.py` (independent golden model), `mac_cluster_scoreboard.py` (multiset comparison — randomized producers can legitimately produce duplicate result tuples, so the original directed test's `got_a != got_b` idiom doesn't generalize — plus an independent stale-read detector cross-checking the hierarchical monitor's real RTL toggle count against how many fresh captures the CPU-visible protocol accepted), `mac_cluster_coverage.py`, `mac_cluster_sequences.py`, and five `tests/test_*.py` files built as a strict checkpoint sequence (env boot → directed port → timed smoke run → scoreboard-verified directed run → base coverage → race-adjacent grafts → full closure run).

One piece of shared, portfolio-wide infrastructure was fixed as its own first checkpoint, with an explicit blast-radius check: `p3_functional.py`'s checkpoint-cache dependency list only watched `verification/uvm/tests/test_*.py`, not the rest of `verification/uvm/` — meaning an edit to `mac_cluster_coverage.py`'s own bin definitions would not have invalidated the cache, silently carrying a stale PASS forward. Widened to `verification/uvm/**/*.py`; re-ran `fpu_top --step functional` afterward (one expected cache invalidation, then stable, 20/20 + 4/4 tests unchanged) to confirm no regression on the one other IP that already used this pillar's pyuvm tier.

### Real bugs found building the closure sequence itself — none in the RTL, all in getting constrained-random traffic right

Unlike Phases 1-3, where every real bug found was in the RTL, every real bug this phase found was in the *verification environment itself* — a reminder that a constrained-random layer is new, non-trivial code with its own correctness obligations, not a free layer bolted on top of already-proven RTL. Several were found by hand while building the closure sequence; a dedicated adversarial-review pass (parallel reviewers across every new file, each finding adversarially re-verified by an independent skeptic before being trusted) then ran over the completed tier before this phase was called done, and found four more — including a real flaw in one of the hand-found fixes below. That review is itself part of this phase's own discipline, not a formality: three of the four bugs it confirmed would otherwise have shipped silently, one of them (Bug D) inside a test whose entire purpose was to catch exactly that class of bug.

**Bug A — a sticky CSR bit, tracked in the wrong scope.** `tile_ni.sv`'s `mesh_egress_en_i` is a sticky, level-held per-tile bit (already known from Phase 3's own history) that reflects whichever `mesh_egress_en` value that tile was most recently pushed as a *source* with — forever, until pushed as a source again. `MacClusterClosureSeq`'s first version picked a random forward destination per iteration with no memory of this: a tile used as a forward source in an early iteration, later picked as a *destination* by an unrelated later iteration, silently re-forwarded its own newly-computed result back into the mesh instead of capturing it. A poll waiting on that tile's own `EXIT_VALID` then waits forever for a capture that structurally cannot happen — confirmed empirically as a real, reproducible hang (raising the poll timeout 10x did not fix it, ruling out a budget problem). **Fixed** by tracking each tile's current `mesh_egress_en_i` value locally in the sequence (`self._me`) and restricting forward-destination choice to tiles currently at 0, falling back to a loopback push (always safe — it resets its own bit) when none are available.

**Bug B — an exception raised inside the driver's own shared coroutine cannot be caught by the calling sequence.** `MacClusterDriver.run_phase` is one coroutine for the entire test (`while True: get_next_item() / item_done()`). The first version of `ConcurrentEgressReconfigSeq`'s bounded-timeout entry push raised an `AssertionError` from inside `_do_entry_push` on starvation, wrapped in a `try/except` around the *sequence's* own `.start()` call in the calling test — this does not work: the exception originates in the driver's independent task, not the sequence's call stack, so it kills the driver's `run_phase` for every subsequent item in the test, not just the timed-out one. **Fixed** by having the driver set `item.starved = True` and return normally instead of raising, mirroring the same write-back-onto-the-item convention already used for `result`/`result_seq`/`result_rejected`. The same shape was later found (by the adversarial review) in `_do_weight_load` and `_do_poll_exit` too — both now follow the same convention; `_do_poll_exit`'s own fix turned out to be load-bearing for Bug D below, once real polling exposed a timeout that a raise there would have hidden as a crash instead of a diagnosable result.

**Bug C — a BUSY probe taken too early to predict a gate decision made later, found and then found to be INCOMPLETELY fixed.** `ReloadWhileBusySeq` probes `STATUS.BUSY` once, then issues a 5-beat AXI write sequence (4 weight rows + 1 CTRL write) that actually attempts the reload; `axi4stream_ctrl.sv`'s own `weight_we_gated = weight_we_i && !busy_comb` is evaluated at the much later CTRL-write commit, not at the earlier probe. `MacClusterClosureSeq`'s first version used the probe's `observed_busy` value to decide whether to re-sync the reference model's weight state — wrong, because the two moments can disagree in either direction. This silently desynced the golden model from real RTL state, surfacing many iterations later as 177/300 scoreboard mismatches with no clear proximate cause. A first fix read back `TILE_WEIGHT_ROWx` after every reload and trusted that instead — the adversarial review caught that this is ALSO wrong, for a different reason: those registers are an unconditional SW-write mirror in `mac_tile_axi.sv`'s own regfile (confirmed absent from its `hw_we[]` list), so a read-back always reflects what was just *written*, not what the PE array actually *latched* into its own `weight_q` — the same class of bug one layer deeper. **Actually fixed** two ways: (1) `_do_weight_load` now samples `STATUS.BUSY` as the *last* action before the real CTRL-write commit (not before the 4 preceding row writes), giving `ReloadWhileBusySeq`'s own `observed_busy` a far tighter, though still best-effort, signal; (2) reference-model correctness no longer depends on inferring the outcome at all — `MacClusterClosureSeq._reload` (and, once the same staleness produced real tile-0 mismatches there too, `test_race_adjacent.py`'s own reload loop) now issues a second, unambiguous `WeightLoadSeq` once the tile is confirmed idle (proven by a real poll having just succeeded) and syncs to *that* — zero inference, correct by construction.

**Bug D — the test built to catch races never actually checked anything.** The adversarial review's single most serious finding: `test_race_adjacent.py` never issued a single `POLL_EXIT` anywhere in its call graph. `ConcurrentEgressReconfigSeq`'s own drain used raw-CSR reads (by design, to avoid a blocking wait that would serialize away the very race it creates), and the reload-attempts loop never polled at all — meaning `mac_cluster_driver.py`'s `exit_ap` was never fed, `MacClusterScoreboard._on_exit` never ran, and `stale_read_violations()`/`sb.unexpected` stayed trivially clean *regardless of what the DUT actually did*. The test's own `report_phase` claimed these were "the real signals" while they were structurally inert — confirmed empirically, not just by static reading: the existing run log showed `0 matched / 0 unexpected` even after real racing had occurred. **Fixed** by issuing a real `CsrPollSeq` poll after every racy sequence in both loops, verifying without suppressing the race (the race has already happened by the time the poll runs). Turning this verification on for the first time immediately surfaced two more real issues (Bugs C's tile-0 sibling above, and Bug E below) — direct evidence the fix was doing real work, not just adding inert instrumentation a second time.

**Bug E — a starved push's data doesn't stop existing just because the testbench stopped waiting for it.** Once Bug D's real polling was active, a genuine scoreboard "unexpected" appeared on tile 3 — not a stale-read, not a timeout, an actual wrong-value observation. Root cause, traced via targeted scoreboard instrumentation: `tile_ni.sv`'s `entry_push_i` set condition is `entry_push_i && !entry_pending_q`. `ConcurrentEgressReconfigSeq`'s `push_own` always targets the same `CONSUMER_TILE` across iterations; when one iteration's push starves (its own poll gives up, but `entry_pending_q` is a real RTL register that does not care that the testbench stopped watching — the push is still genuinely pending), the *next* iteration's own push-attempt to that same tile is silently a no-op (its CTRL write's `entry_push_i` pulse cannot re-latch while `entry_pending_q` is already 1). The original code only published `entry_ap` on *confirmed* acceptance, so when the first, still-pending push was *finally* served, the second item's own poll observed `!ENTRY_BUSY` clearing and incorrectly attributed that service to itself — publishing the wrong item's metadata against the RTL's actual (older) data. **Fixed** by publishing `entry_ap` unconditionally right after the CTRL write's own commit, describing what's actually true at that moment (the data has been submitted and its processing has begun) rather than gating on a confirmation that cannot distinguish "my push was served" from "an older pending push was served instead of mine." A silently-dropped duplicate now shows up as scoreboard leftover (already tolerated, not a failure signal in this test) instead of manufacturing a false "unexpected."

**Two coverage-methodology findings, documented rather than redesigned under time pressure**: `cp_poll_to_transition_offset`'s three negative buckets (`<=-3`, `-2`, `-1`) are *structurally* unreachable, not just hard to hit — `_do_poll_exit` only ever samples an offset *after* observing `EXIT_VALID=1`, i.e. at-or-after the real toggle, and simulation time cannot run backward from that computation. An earlier version of this file's own docstring claimed "randomized cadence populates this bin for free" — wrong; fixed to state the real limitation. Separately, `overall_coverage_pct`'s unweighted mean across covergroups of very different bin cardinality (2 to 16 bins) gives `cp_ingress_mux_contention` a fixed +6.25 percentage-point floor on the headline number regardless of whether real contention was ever exercised (its `CONTENTION_NOT_SEEN` bin is trivially hit on the first sampled edge of any test). Both are now called out in `mac_cluster_coverage.py`'s own docstring/property comment rather than left as an implicit, easy-to-misread number.

## Phase 5 Addendum: Mesh Deadlock/Starvation Hardening

_Everything above this line is the Phase 3/4 record as it stood at the time, left unmodified. Phase 5 targets an open item Phase 4 empirically confirmed but did not fix: `tile_ni.sv`'s ingress mux gives the mesh unconditional priority over a CPU entry push with no bound at all (its own header comment called this "arbitrary but simple"), and `ConcurrentEgressReconfigSeq`'s own docstring records this as a real, reproducible mechanism, not a hypothetical. Scoped, via `AskUserQuestion`, to hardening the *existing* 2x2 mesh (deadlock-freedom is structural to XY routing regardless of mesh size — growing to 3x3/4x4 is a separate, later goal that does not itself change this) rather than dimension scaling._

### Two gaps, one fixed this phase, one correctly deferred

A dedicated research pass (an Explore agent reading full files, not summaries) found two distinct, independently-real gaps, not one:

1. **`tile_ni.sv`'s ingress-mux fairness** — no bound at all on how long a CPU entry push can lose to sustained mesh traffic. This is the gap this phase closes.
2. **`mesh_router.sv`'s `rr_arbiter` instances tie `burst_lock_i=1'b1` permanently** — correctly, it turns out: this fixes a real VALID-STICKY data-corruption bug a Phase 3 checkpoint caught in BMC (see that phase's own Bug 1). But it also permanently invalidates `rr_arbiter_liveness.sby`'s own `assume(!burst_lock_i)`, so `STARVATION_FREE`'s "granted within N_REQ cycles" guarantee does not cover the real composed wiring — `mesh_router.sv`'s own header already says this honestly ("bounded-latency delivery under contention remains a cover, not a safety, property"). Closing this for real needs the credit-based flow control Phase 3's own plan named and deferred (a tile only wins mesh arbitration toward a destination that has already reserved capacity to accept it) — genuinely substantial new engineering, not a quick re-proof. **Correctly scoped out of this phase, not silently left uncovered**: an initial plan draft (a Plan-agent design pass) argued Checkpoint A below was unsafe to ship without also building an NI-boundary flow decoupling mechanism to close gap 2 — a dedicated adversarial-review workflow (four independent agents checking the plan's concrete claims against the real RTL) found that argument itself was wrong: the baseline hold via `tile_s_axis_tready_i` alone is *already* unbounded, so a *bounded* fairness fix cannot make it "unsafe." Checkpoint A is independently complete and safe to ship alone; the NI-boundary decoupling remains a legitimate, separate throughput improvement, not built this phase.

### Checkpoint A: `tile_ni.sv` ingress-mux fairness bound

`entry_starve_cnt_q`, a new saturating 3-bit register, counts consecutive *real* mesh transfers (`tile_s_axis_tvalid_o && tile_s_axis_tready_i`, never a raw cycle count — a cycle counter would inflate during a downstream freeze and make the bound unstatable) that occur while an entry push is pending and losing. `src_is_mesh_q`'s existing re-decision gate is unchanged in *when* it fires (still only at idle or just-consumed, preserving the existing VALID-sticky property unmodified) but now also checks `!(entry_pending_q && entry_starve_cnt_q >= FAIRNESS_LIMIT)` (default `FAIRNESS_LIMIT=2`), forcing entry to win once the bound is reached.

**A real off-by-one, caught before it shipped.** Both the counter's update and the mux's fairness check read `entry_starve_cnt_q` from *before* the same-cycle transfer that increments it — the two agents running the adversarial review's counter-edge-case check and its safety-argument check independently converged on the same finding: the RTL actually enforces `entry_starve_cnt_q <= FAIRNESS_LIMIT + 1`, not `FAIRNESS_LIMIT`, confirmed by a hand-traced 4-cycle sequence. Fixed by stating the verified bound (`FAIRNESS_LIMIT+1`) rather than patching the gate arithmetic to chase the tighter, untested one.

**Formal**: a new `tile_ni_liveness.sby` (mirroring `rr_arbiter_liveness.sby`'s own split from its safety proof — an `ifdef LIVENESS` nest inside the existing `ifdef FORMAL` block, so `tile_ni.sby`'s existing BMC scope/depth is unchanged). First attempt at `mode prove` failed temporal induction — not a real counterexample (the basecase passed cleanly to depth 8; only the induction step failed), the classic k-induction gap where the property alone doesn't carry enough state for the solver to rule out an unreachable predecessor. Hand-derived the missing auxiliary invariant directly from the RTL's own construction (`entry_starve_cnt_q >= FAIRNESS_LIMIT+1 -> !(entry_pending_q && src_is_mesh_q)` — the cycle the counter reaches its cap is exactly the cycle `src_is_mesh_q` gets forced to 0, they change together, never with `src_is_mesh_q` lagging), added it as a second assert, and k-induction closed in 1 induction step. A genuine inductive proof, not a bounded-depth fallback.

**A real Verilator lint catch, fixed cleanly**: `entry_starve_cnt_q >= FAIRNESS_LIMIT` triggered `WIDTHEXPAND` (3-bit signal against a default-32-bit `int` parameter) — P1 and P4 both failed on this before it was caught. Fixed with an explicit `3'(FAIRNESS_LIMIT)` cast at all three comparison sites, applied consistently even where Yosys's own formal flow hadn't flagged it.

**Verification**: a new, isolated `IngressFairnessSeq`/`test_ingress_fairness.py` — deliberately does *not* reuse `ConcurrentEgressReconfigSeq`, whose own docstring identifies its observed starvation as *dominated* by a different, unfixed-by-this-checkpoint mechanism (an undrained single-slot exit buffer freezing the array). The new sequence fully drains both results every iteration so that freeze mechanism cannot engage, isolating whatever the fairness bound alone produces. **Result: 0/20 iterations starved**, 40/40 scoreboard matches, 0 stale-read violations — confirms the formal bound empirically, in isolation from the mechanism it doesn't address. Re-running `test_race_adjacent.py` unmodified (which mixes both mechanisms) showed the honestly-predicted partial effect, not a full fix: entry-pushes-not-accepted dropped 6→5, `ingress_mux_contention` stayed 100% — that sequence's own docstring was updated to record that one of its previously-observed starved pushes was in fact raw mesh-priority contention, now fixed, while the remainder is the freeze mechanism this checkpoint doesn't touch.

### Result

**Standalone `mac_cluster` 9/9 PASS** (118,342 cells, +94 from Checkpoint A — well under the plan's own pre-scoped 1,000-2,000-cell estimate since only the fairness fix landed, not the NI-boundary skid; TT +5.702 ns MET, SS -147.088 ns advisory unchanged, GLS PASS). All 6 pyuvm tests pass (the new `test_ingress_fairness` plus the existing 5), stable, no regression. `rv32i_soc`'s flat copy of `tile_ni.sv` (`rtl/` and `verification/`) was stale after this fix and has been re-synced; the SoC-level sweep result is recorded in this IP's own composition record.

**What Phase 5 actually delivered**: a formally-proven (genuine k-induction, not a fallback), empirically-confirmed (isolated regression + honest partial-effect confirmation in the pre-existing racy test) bound on CPU-entry starvation — closing the one gap that was genuinely unbounded with no mitigation at all. **What remains open, by explicit, correctly-scoped decision, not oversight**: the exit-buffer-freeze mechanism `test_race_adjacent.py` still shows (a `mac_tile_axi`-internal design choice, out of this phase's mesh-scoped boundary); the `rr_arbiter`/`burst_lock_i` "granted vs. transferred" gap under real backpressure (still cover-only, credit-based flow control remains the correctly-deferred future task Phase 3 already named); and — the one quantity no RTL change in this phase or a future credit-based one can bound — CPU acknowledgment latency on the exit register, a software timing contract, not a hardware one, the same honesty boundary `mac_tile_axi`'s own `CTRL.RESULT_ACK` already lives with.
